### The weather post (`weather.py`)

Conditions at the seed pile (issue #25, re-instrumented in #51): a house-box service on orchid (needs neither GPU nor camera, just the bus, the gateway, and internet) with **two sources and one truth**. The driveway's own station — an **Ecowitt GW2000B gateway + WH90 sensor array** on the LAN — is the system of truth for everything it can measure: polled every 60 s over its unauthenticated local HTTP JSON API (`/get_livedata_info`), it supplies temp, feels-like, dew point, VPD, humidity, wind speed/gust/max-daily-gust/direction, solar, UV, the piezo rain suite (raining-now bit, rate, event/day/week/month/year totals), barometric pressure (abs + rel, from the gateway's internal WH25), indoor temp/humidity, and the WH90's battery/voltage (radio signal comes from `/get_sensors_info`, fetched on the slower cadence). **OpenWeather's classic free APIs keep exactly two jobs the station can't do**: the 5-day/3-hour forecast (hourly) and the sky garnish — condition text, sunrise/sunset, and the station's **lat/lon** (issue #111: read from the response's `coord`, so a `MERLE_WEATHER_LOC` given as a bare zip still resolves to real degrees; the dashboard needs them to compute sunrise/sunset for any day but today, for the deep-pan night bands) — from a demoted 10-minute `/weather` call whose measured fields are discarded. Measured fields **never** fall back to OpenWeather: a gateway outage is a skipped poll and a chart gap, never a silent source switch. Publishes the retained `weather/*` topics; consumers are the station view and the narrator's prompt context (issue #26, `weather/current` only).

- **Config** (env, the MERLE_MQTT conventions): `MERLE_OWM_KEY` is **required, no default** — a service that would poll 401s while looking healthy fails at startup instead. `MERLE_ECOWITT` (gateway `host` or `host:port`, e.g. `192.168.1.210`) names the system of truth at home — and its **absence is a mode, not an error** (#301): with no gateway configured, Willard runs **OWM-only station mode** for the remote stations of epic #212, promoting the demoted `/weather` call back to the current source at the 10-minute garnish cadence. The payload is `parse_current`'s shape — temp, feels-like, humidity, **wind** (Earl's wind rule gets a real number on a box with no anemometer), sky, sun, lat/lon — plus since **#428** free `/weather` also fills **sea-level pressure** (`pressure_rel_inhg` from `main.pressure` hPa) and a **computed dew point** (Magnus from temp + humidity; OWM does not publish dew on this endpoint). **UV, piezo rain, solar, indoor, battery, radio** stay honestly absent (UV needs One Call, not free Current Weather). Every payload carries **`source`: `"owm"` | `"ecowitt"`** so the station view can dim **the station itself** ("Station not available") instead of painting a wall of sensor dashes; missing `source` on old retained messages is treated as instruments present. `ts` is OWM's own observation time, so the history window records each fresh report and dedupes re-served ones. At home the truth split is unchanged (measured fields still never fall back to OpenWeather; `merge_current` sets `source: "ecowitt"`), and losing the var announces itself: the on-duty line says STATION MODE in capitals precisely because at home that line means a misconfiguration, not a new station. `MERLE_WEATHER_LOC` takes `zip`, `zip,CC`, or `lat,lon` (default `49001,US` — the station's home turf; lat/lon is recognized because both halves parse as floats, which a country code never does). `MERLE_WEATHER_HISTORY` overrides the history-file path.
- **Gateway parsing** (`parse_station`): the GW2000B keys live data by opaque ids (`0x02` temp, `0x0E` rain rate, `"3"` feels-like…) and wraps every number in a unit-suffixed string (`"29.24 inHg"`, `"46%"`); `STATION_COMMON_IDS`/`STATION_RAIN_IDS` are the Rosetta stone (verified against the real device) and `station_num()` strips the units. A response where nothing parses is treated as a failed poll, not a report of Nones. The `weather/current` payload is a **superset of the pre-#51 shape** — every old field name survives with its old meaning, so the narrator and any open dashboard tab ride through a deploy; `ts` is our fetch time (the station has no observation clock).
- **Timestamps on the weather topics are unix epoch seconds**, not the ISO strings used elsewhere: the dashboard formats them in the viewer's locale and the narrator compares against `time.time()` for staleness — nobody wants to parse.
- **Forecast points carry precipitation** (issue #56, un-summed in #65): besides `pop` (probability 0..1), each `weather/forecast` point has `rain_rate_inhr` — the step's `rain["3h"]` mm converted to an **average in/hr over the 3-hour window ending at the point's `ts`**, sharing the observed piezo trail's unit — and `snow_3h_in`, the step's `snow["3h"]` mm as plain inches (its own strip charts it per step; no station instrument shares a scale with snow, the piezo is snow-blind). OWM omits both objects entirely on dry steps; the fields default to 0, not null: a step the forecast left dry is a real forecast of zero, unlike a station gap (which stays an honest hole in the observed trail).
- **The 48h rolling window** is the live state the service owns: polls run every 60 s but the trail keeps **5-minute resolution** (`should_record` gates appends; ~576 points of the 12 charted fields, tens of KB), pruned by age *measured from the newest point* (deterministic for tests), republished whole to `weather/history` on every append, and persisted to a JSON file beside the service so restarts don't blank the dashboard's observed trail. Old history files load fine — pre-#51 points simply lack the new fields, which chart as gaps that heal within 48h. Deliberately a flat file, not SQLite — bounded, rewritten whole, refetchable.
- **The seasonal archive** (`weather_archive.py`, issue #105) is the permanent record beside that window, and the two are not alternatives: every point that passes `should_record()` is appended to the window **and** recorded to a SQLite `observations` table that never prunes. The window stays the retained-bus payload (a fresh tab rehydrates its trail from the broker with no fetch — the contract that keeps weather off HTTP); the archive is a second consumer of the same tick, read over HTTP only when someone asks for the deep past. A failed archive write is logged and skipped — one missing point is a gap the chart already draws honestly, and never worth killing a service whose job is the bus. Startup backfills the window into the archive (idempotent on every restart, not just the first, so a fresh archive inherits up to 48 h of real readings). Config is `MERLE_WEATHER_DB` (default `weather.db` under `WorkingDirectory`), and an unopenable path fails at launch rather than publishing weather for a week while recording none of it. Four decisions worth the ink:
  - **On the house box, not in `merle.db`.** `merle.db` lives on bluejay next to the daemon, and daemon-down is the *steady state* for the 24/7 dashboard — archiving through the daemon's HTTP surface would punch holes in the record exactly when bluejay naps, which is most of the time. `weather.py` runs on the always-on box (orchid) 24/7, so the rows live where the writer lives. This is `frame_archiver.py`'s reasoning applied to a different kind of byte: house-resident writer, house-local store, an MCC route on the same box reading off local disk, never a `/daemon/*` endpoint. `storage.py` and `merle.db` are untouched.
  - **5-minute rows, not an hourly rollup.** Issue #72 proposed hourly because that's all its forecast scorer needs, but 5-minute data is a strict superset — hourly means, min/max, and vector-averaged wind all derive from it at read time — and it's what the station already records and the charts already draw. Hourly would throw away resolution we have and cap any pressure curve at a day's zoom. ~105 k rows/year, which SQLite does not notice. **#72's hourly rollup is therefore a query, not a store**, and these rows are the `observations` table its scorer joins forecasts against.
  - **Epoch seconds, not ISO-8601 — a deliberate divergence from `storage.py`.** Every other table in this project stores ISO strings; this one stores integers. The weather bus is epoch end to end, the points arrive as epoch, and the chart consumes epoch, so converting at the store boundary and back at the route boundary would be two lies for zero benefit. (#72's forecast rows keep ISO because they juggle multi-source issuance times; a single-source observation stream has no such problem.) `ts` is the PRIMARY KEY, which SQLite aliases to the rowid — so the range scan is already indexed, and re-recording a point the archive has is a no-op rather than a conflict: `roll_history`'s dedupe rule enforced by the store. Append-only, no UPDATE path. Columns are exactly `HISTORY_FIELDS`; a test asserts the two can never drift apart.
  - **The archive is the one irreplaceable file the stack owns.** Every other piece of state here is a cache of something re-fetchable — `weather_history.json` refills in 48 h, frames re-archive, `merle.db` re-derives. A deleted observation is a moment of driveway weather no API sells back. `toddtech-infrastructure/servers/Orchid.md` § Backups says so where it can be acted on.
- **Resilience**: any gateway or OpenWeather failure means a skipped report (logged, the next 60 s pass retries — garnish and forecast timers stay put on failure rather than waiting out their full cadence), never a dead service; OWM errors are logged without the URL, which carries the API key. The bus side inherits `EventPublisher`'s run-with-or-without-broker contract.
- **Deployment**: runs on orchid as `willard-weather.service` (#371 Phase 3; see Services on orchid under Quick start in [the hub](../../TechnicalGuide.md), and `toddtech-infrastructure/servers/Orchid.md` § The weather post for the recipe). The unit carries `MERLE_MQTT=mqtt.lan:1883`, `MERLE_ECOWITT=192.168.1.210`, `MERLE_WEATHER_DB` (absolute), `MERLE_OWM_KEY` via `EnvironmentFile=/etc/merle/orchid-weather.env`, and — for the on-air segment — `MERLE_OLLAMA=192.168.1.79:11434` (bluejay's GPU, same as the narrator unit); `WorkingDirectory` is the repo checkout, which is where the default-pathed `weather_history.json` lives. One-time hardware note: the gateway's altitude/relative-pressure calibration is set in its own web UI — until then `rel` equals `abs` and "sea-level pressure" is a polite fiction.
- **Willard's on-air segment** (issue #45): every `REPORT_INTERVAL_S` (30 min, first one on the first loop pass), the service narrates the conditions + next-24h outlook through the narrator's LLM tier — same `MERLE_OLLAMA`/`MERLE_OLLAMA_MODEL` env vars, same kill switch (unset = no `weather/report` topic at all, everything else unchanged), and the same client code: `weather.py` imports `ollama_client.Ollama` (the one client, lifted out of the narrator by #628) and calls its generic `complete()` rather than growing a second copy that could drift. The persona is an exaggerated **Willard Scott** homage (booming folksy showmanship), a constant in `weather.py`. Since #670 his viewers are everyone who lives at the house: the family (never named: the prompt is public, and a nameless family is one the model can't invent names for), the birds at the feeders and in the trees, and the squirrels, deer and rabbits. The camera era's "squirrels and turkeys of the driveway" are gone. He also knows where "here" is: `load_yard()` reads the feed registry's `yard:` description once at startup (`feeds.yard()`, #636, the same text the field notes get), and `report_system_prompt(yard)` sets it between the persona and the rules as a `Where the station sits:` paragraph. A registry without one (every station today) gets exactly the persona-plus-rules prompt, and a registry that fails to load costs the paragraph, never the broadcast. The persona is rather than a `personas/*.yaml` — that system carries narrator-only machinery (`mqtt_id`, pacing, TTS), and Willard is a reporter, not a narrator. The prompt follows the narrator's desk-tested labeled-paragraph shape: a dry `current_facts()` paragraph (since #51 including the station's dew point, rain-falling-now + rate, rainfall today, UV when ≥1, and the barometer — each only when measured, Willard never narrates a hole), a dry `outlook_facts()` paragraph from `forecast_digest()` (next-24h high/low, strongest wind or gust, peak precipitation chance, expected rainfall in inches — each step's #56 rate × its 3 hours, summed — expected snow in inches on its own ledger (#65: Willard says "two inches of snow", never folds it into the rain number), and conditions in order of appearance), a dry `extended_facts()` paragraph from `extended_digest()` (issue #60: one terse weekday-labeled line per local calendar day after today, all ~5 days the API publishes; tomorrow deliberately overlaps the rolling 24h outlook — today in detail, the week at a glance, the way a broadcast desk talks), then the cue; all flavor lives in the persona, and the rules tell Willard to close with a sentence or two picking out the days that matter, never reciting the list (desk-tested live: he singles out the soaker and the nice one). Output is `sanitize_report()`-cleaned (collapses whitespace within paragraphs but *keeps* the paragraph break, unlike the narrator's one-line `sanitize_line`), then `finish_sentences()` (#673) trims a segment the `REPORT_NUM_PREDICT` cap cut off back to its last complete sentence and logs how many characters went. The cap is 360 tokens, raised from 280 after six uncapped `gemma3:12b` takes of the house prompt ran 202 to 271 tokens and a live segment aired cut off mid-word. The trim is the guarantee and the cap is only headroom, and a reply with no complete sentence skips the broadcast and published retained as `{ts, text, model}` (`ts` epoch seconds, the weather-namespace convention). Failure = a skipped broadcast retried on the next 10-minute pass (the forecast-retry pattern) — and since #335 an **unreachable** host is transition-logged rather than announced on every attempt: one line when it goes away, one when it returns, silence between. Bluejay is a workstation that is off (or Ollama-less) most of the time by design, and Willard's retry cadence measured **41 error lines an hour** for a service in perfect health — the #35 journal-spam disease, where the noise buries what matters and a wall of red makes a working system look broken. The transition state lives on the shared `ollama_client.Ollama`, so the narrator and the Aviary's analysis pass inherit it. A host that *answers badly* (an HTTP 500, unreadable JSON) stays loud every single time: this removes noise, it does not swallow errors; a current report older than `REPORT_MAX_AGE_S` (30 min) skips the broadcast rather than narrating yesterday's rain. The blocking Ollama call is safe here — it runs on the main loop's own thread (not paho's; `EventPublisher` has its own network thread) with 10 minutes of slack per pass. — `EventPublisher` grew an optional `status_topic` (Last Will `offline` + retained `online` on every (re)connect, offline published on `close()`), so any future bus process gets presence for one constructor arg. The Last Will fires on any socket death without an MQTT DISCONNECT — a crash, but also systemd's SIGTERM — so `systemctl stop` flips the dashboard within seconds with zero signal handling; the `KeyboardInterrupt` handler covers graceful manual runs. Freshness (`STALE_AFTER_S`) remains the *online-but-not-reporting* signal and the whole judgement when no retained status exists (a pre-#31 service).
- Pure logic (config/location parsing, gateway live-data + sensor-roster parsing, OWM response → bus payload mapping, the station/garnish merge, window roll/prune/thin/persist, segment prompt assembly/digest/sanitation) is covered by `test_weather.py` — the Ecowitt fixture is lifted verbatim from the real GW2000B; the fetch loop, MQTT plumbing, and live Ollama call are desk-tested against the real services (`weather/current` payload round-trips a fresh subscriber intact).

### The station view (`/aviary/weather`)

The GUI half, in `web/` ([web.md](web.md) for the process, the unit and the design language). The bullets below moved here from the retired dashboard spoke in #628; the view they describe was built as the dashboard's overlay and is now the Aviary's weather tab (#652).

- **The station view** (issue #51, `WeatherStationView` in `web/components/WeatherStationView.tsx` since #628): mounted under the Aviary masthead as the `/aviary/weather` page since #652 (`AviaryWeather` in `components/Aviary.tsx` composes the masthead, `tab="weather"`, over the view). The overlay contract it was born with — `fixed inset-0 z-50` over an opaque `--bg`, body scroll locked, Escape or a close control to exit — left with #652: it is a plain `<section>` now, the page scrolls, the masthead navigates. Its own heading row stays (Weather Post · station view, with Willard's lamp: on duty / no fresh report / on coffee break) minus the close control and the rule beneath it, which would have sat one line under the tab bar's. No `requestFullscreen`: it's a page of instruments that should scroll on phones. Left column: hero conditions (big temp + the WxStat grid: dew point, humidity, wind + gusts + max daily, barometer + tendency, UV + solar, rain today + falling-now lamp; rain ledgers and VPD in a fine-print line — the four less-self-explanatory metrics carry a **circled-i info affordance** (issue #63): a quiet icon after the stamp label whose hover or keyboard focus reveals a field-manual note in the readout chip's dress explaining how the station measures it and what the number means; pure CSS via `group-hover`/`group-focus-within`, an absolute overlay so revealing it never shifts the grid, `tabIndex` so touch taps and keyboards get it too) and the trend chart writ tall — a **144h window** (issue #60: a 24h trail + the full 5 days the free API publishes, "now" at the 1/6 mark; fixed span, never sized to the payload, so a short forecast leaves the far end honestly blank instead of reflowing the axis) plus **three instrument strips sharing its time axis** (rain-rate bars in weather blue, the barometer's wander, solar in turkey yellow with UV dashed on its own scale), so every timestamp lines up vertically across all four. At that span hour-offset ticks stop meaning anything, so the gridlines are the **viewer's local midnights** (`dayTicks` in `lib/weather.ts` — DST-safe 36h-then-refloor stepping, Vitest-covered) and the axis reads as a calendar: each short weekday label centered over its day's slice, with narrow edge partials and anything shadowing the "now" stamp suppressed (the hover chip names every point anyway). The frame is the Aviary page's (`max-w-[1500px] px-4 py-6`, the old dashboard's measure; the right rail is fixed 320px, so the extra width all goes to the chart). The strips chart the observed trail — the forecast carries none of those series, and the honest blank future half of each strip is where the series label sits. Two exceptions. **The rain strip changes units at the now line** (issue #65, superseding #56's volume bars): the observed half is the piezo's measured in/hr (ceiling from observed points only), the forecast half is the **chance of precipitation** — `pop` as ghost bars on a fixed 0–100% scale (full strip = certain), the same `--rain` ink as the observed bars but shaded by chance and ceilinged below their full voice (issue #113), each spanning the 3-hour OWM window ending at its point, clipped at the now line. Chance is what a viewer plans around; the forecast's volumes read as slivers on the piezo's scale and live in the hover chip instead. **Snow is its own strip** below rain, forecast-only ghost bars of `snow_3h_in` in snow-white ink (`--ink`, never the rain's blue), shaded by depth to full white for the heaviest (issue #113), with its own ceiling (floor 1 in/3h, so a dusting hugs the baseline) — the observed half is honestly blank forever (the piezo cannot see snow), and the strip is **seasonal** (issue #69, the owner-sanctioned exception to the reserve-the-space rule): hidden April–October instead of sitting dead for seven months, shown November–March (`snowSeason`, `lib/weather.ts`), with a safety valve — a forecast actually carrying snow shows the strip in any month, so the calendar gate can only ever hide an empty row, never data. One crosshair spans the whole stack; the readout chip gains a station line (rain rate, baro, solar, UV) on observed points, and on forecast points the expected rain rate, snow inches, and chance (`pop`, shown from 5% up; rates that would print as zero stay quiet). Right rail: Willard's segment with display-face room to breathe (the #92 rail + sky stamp), then "the station itself" — the indoor strip, absolute pressure, WH90 battery (5-segment meter, LED→turkey→chipmunk as it drains) + voltage, radio signal (4 segments), last-report age. The battery row prints its **voltage first and the meter last** (issue #103) so the two green meters share a right edge and read as one column — a meter placed before its voltage is the only thing in that box that can't line up with the row beneath it. Indoor readings and hardware health share that box deliberately: both are "the station", not "the weather".
- **Chart mechanics the view inherited from the dashboard's Weather Post panel** (#25, #40, #71, #78, #111; the panel retired in #628, the mechanics did not). The hand-rolled SVG trend chart draws the observed trail solid to the left of a dashed "now" line (from `weather/history`) and the forecast dashed to the right (from `weather/forecast`, bridged at the last observed point so the lines meet), wind on its own scale underneath. **The forecast's temperature is station-calibrated at render time** (issue #71, `blendForecast` in `lib/weather.ts`): the offset between the last observed temperature and the forecast's opinion of that same moment (linearly interpolated) is added to every forecast temp, decaying linearly to zero across `BLEND_HORIZON_S` (12 h) — MOS-style bias correction anchored to the instrument of record, not cosmetic smoothing, closing the ~5 °F cliff the OWM grid cell's bias against the driveway's microclimate used to draw at the seam. Temperature only (an additive offset on the station's sheltered wind would go negative); it runs inside `trendSeries`, so the hover chip reads the calibrated values and the chart and its readout never disagree. Render-time rather than publish-time on purpose: the seam is drawn against a station point minutes old, so a blend baked in at the hourly forecast publish would re-gap whenever temperature moves fast — and the bus payload stays OWM's actual forecast (the never-silently-switch-sources ethos; Willard narrates the raw numbers). The conditions block reads the station (#51), each value rendered with em-dash placeholders so data landing never shifts anything; barometric pressure groups with the atmosphere despite being measured indoors — pressure is sky, not room. The barometer's tendency (`pressureTrend`, `lib/weather.ts`) compares the newest observed reading against the one nearest 3h earlier — real points, never interpolation — with ±0.02 inHg as meteorological "steady" and no opinion on a trail shorter than half the span; since #67 the core is the series-agnostic `seriesTrend(history, now, value, eps)`, run over temperature (±1.5°F), dew point (±1°F), and humidity (±3 points) too — temp/humidity arrows mostly ride the sun, honest but diurnal, while a moving dew point means the air mass itself is changing. **A condition icon rides left of the temperature** (issue #78): eight hand-drawn SVG glyphs (`ConditionGlyph` — sunny, mostly sunny, partly cloudy, cloudy, stormy, raining, snowing, super windy) in the house line-work style — structure strokes inherit `currentColor` so stale/off-air dims them with the text, the subject of each sky (sun disc, rain, lightning) wears its accent (`--turkey`/`--led`) only while the report is fresh, and clouds fill with `--panel` so overlaps occlude. Which sky wins is `conditionIcon()` in `lib/weather.ts` (Vitest-covered), precedence drama-first: Thunderstorm > Snow > Rain/Drizzle-or-piezo (`raining === 1` outranks OWM's word — the driveway instrument beats the grid cell) > windy (sustained ≥ 20 mph or gusts ≥ 30, plus Squall/Tornado) > the four cloud-cover states read from OWM's `condition`/`description` (Mist, Fog, Haze read as cloudy for now; night/moon variants are a deliberate follow-up). The icon slot (`ConditionBadge`, 58px) reserves its footprint whether or not a sky is known — no report means an empty reservation, never a collapsed one. The view's own mqtt.js client (`useWeatherFeed`) subscribes to the retained weather topics, so a fresh tab paints weather instantly with zero HTTP. **Willard's on-air segment** (issue #45, voice treatment #92): the retained `weather/report` narration rendered in the display face with a "willard, on the air" stamp + broadcast clock — voice = display type, telemetry = mono, plus the cast treatment: left rail and name stamp in `voiceColor("Willard")` (`--sky`), body stays ink. A segment older than `REPORT_STALE_S` (90 min = three missed half-hour broadcasts) is history, not news, and yields to the between-broadcasts placeholder; the block reserves a fixed min-height **and the rail+pad** either way (no-layout-shift rule) and lives inside the dimmable content, so it fades when Willard is off duty. `parseReport` lives in `lib/weather.ts` with Vitest coverage. The masthead bills the reporter — green lamp + "willard with the weather" when fresh, "on coffee break" the moment the retained `weather/status` reads `offline` (the veil then shows when he last checked in, clock + relative age — the chart's "now" line means nothing once he's off duty — plus the `systemctl start` command), a turkey-lamp stale warning when the report is older than 30 minutes with no offline announcement, "off the air" when there's no report at all. The view reserves its full footprint before data arrives; when off the air, the data skeleton dims to 30% and the what-to-do message overlays it, with bus-unreachable and no-service-publishing kept distinct. **Hover** (issue #40; touch-scrubbing too — `touch-action: pan-y`, so vertical page scroll survives) shows a crosshair + readout chip that **snaps to the nearest real report/forecast point** (`nearestPoint`) — never interpolated values — with day + time, temp, wind/gusts, condition, and an observed/forecast stamp; the chip rides the roomier side of the crosshair and everything hover-related is an absolute overlay, so it can't shift layout. Because the viewBox is stretched (`preserveAspectRatio="none"`), pointer math runs against the container rect and the marker dots/labels are HTML overlays, not SVG text/circles (which would distort). The time axis carries faint gridlines plus near-black night bands (`nightBands`) — one sunset→next-sunrise interval per day, each day's sun times **computed from the station's lat/lon** (issue #111, `sunTimes` — the pure NOAA solar-position algorithm) rather than repeated from today's, so the shading is right at any pan depth. Scale whispers sit on the chart edges: temp min/max on the left (squirrel-tinted), wind ceiling on the right (the two series ride different scales, so a shared axis would lie). Pure parsing/shaping (`parseCurrent`, `parsePoints`, `parseReport`, `trendSeries`, `blendForecast`, `tempRange`, `windCeil`, `seriesCeil`, `pressureRange`, `pressureTrend`, `linePath`, `nearestPoint`, `timeTicks`, `nightBands`, `sunTimes`, `compass`) lives in `lib/weather.ts` with Vitest coverage; temp axis pads to a 16°F minimum span so a flat day reads flat, wind axis floors at 10 mph so calm days hug the baseline, pressure holds a 0.3 inHg minimum span for the same reason.
- **The weather archive's read path** (issue #105, `app/weather/history/route.ts`): `GET /weather/history?from=<epoch>&to=<epoch>` → `{points: [...]}`, the deep past the retained bus window can't carry (a payload republished whole on every append has to stay bounded). The writer runs on the house box precisely so the record is always being kept, and the reader is a route off the same local disk. The body is byte-shaped like a `weather/history` bus payload, so `parsePoints()` reads both and **the chart cannot tell an archived point from a retained one**; the client half is `fetchArchive()` in `lib/weather.ts` — thin `fetch`, hand-mirrored types, throw on non-OK, `cache: "no-store"` (deliberately *not* `immutable`: a time range's contents grow). The range is **clamped to 90 days** at both ends of the wire (`parseRange` here, `clamp_range` in Python — "a typo can't bucket ten years"), anchored at `to`, so `from=0` returns the newest 90 days rather than scanning the table; an inverted range is left inverted because it honestly selects nothing. **Unset `MERLE_WEATHER_DB`, a missing DB file, a malformed range, and an empty range all answer a quiet `{points: []}`, never an error** — on day one an empty archive is the normal state, and "no data here" is a chartable answer the gap-drawing chart already handles. The route has **no default path**, deliberately: `aviary-web`'s `WorkingDirectory` is the `web/` subdirectory while `willard-weather`'s is the repo root, so a shared *relative* default would name two different files and serve an empty archive with no error anywhere — the unit carries an absolute path. The SQLite driver is `node:sqlite`, the stdlib module; its Node-version gotcha lives in [web.md](web.md). #106's pan is this route's consumer.
- **The station chart pans through history** (issue #106): grab it and drag, mouse or finger, and the 144h window slides back over #105's archive — the barometer's wander over a week is the payoff the archive was built for. **The window is state, not a constant**: `null` means live (24h back, 120h ahead, "now" at the 1/6 mark — the view opens exactly as it always has), and once panned it holds an **absolute right edge**, so a window dragged to last Tuesday stays on last Tuesday instead of creeping as `now` ticks under it. That null doubles as the snap-back control's home. **Span is fixed; only position moves** — `clampWindow` (Vitest-covered) preserves the span on every clamp, and when the walls are closer together than 144h the *right* wall wins, which is not an edge case but the young-archive's normal state: the default window must stay exactly reachable on day one. `trendSeries` and `dayTicks` take an **explicit `[ts0, ts1]`** rather than deriving one from `now`; `now` survives in `trendSeries` only as the seam that splits observed from forecast.
  - **The right edge is pinned at `now + 120h` and that is not a bug.** Five days is *everything* OpenWeather's classic free tier publishes and `parse_forecast` caps nothing — the UI truncates no data, so there is no scrollable space to invent behind it. More forecast means a different tier or source (#72's territory).
  - **The left wall is discovered, never announced.** The route has no "oldest reading" endpoint (and #106 adds no backend), so the client simply clamps at the oldest point it holds and asks for one `ARCHIVE_CHUNK_S` (7 days) below it whenever a drag *reaches* for something older. The request keys off what the viewer **asked** for, not the clamped result — the clamp pins `ts0` at the wall, so waiting for the clamped window to cross it would mean the fetch never fires at all. An empty answer means the record stops there and sets `exhausted`, which also stops the asking: without it a drag held at the wall would refetch forever. A **7-day** chunk is what keeps a station outage from reading as the end of the record; a longer one still would. Fetch failure and unset `MERLE_WEATHER_DB` take the same path — the chart is exactly the chart it was before the archive existed and panning stops at the retained window's edge.
  - **Panning the first day costs no network.** The bus already publishes 48h and the view charted only 24h of it, so the second day was being thrown away; it now pans for free. The archive is merged **additively** onto the retained trail (`mergePoints`, deduped by ts — the two genuinely overlap, and the bus wins a tie), never replacing it: the trail still rehydrates from the retained topic with zero fetches. Ranges are fetched once and cached in component state, history being immutable once past. The dedupe that matters is a **ref, not state**: a chunk resolving doesn't re-render synchronously, so a `pointermove` landing between the fetch settling and React catching up still sees the previous render's `oldestKnown` and would re-request the same week — `inFlight` can't catch that, since it's already back to zero.
  - **The axes settle when the gesture does.** Every value scale is computed from the points in view, so a drag would rescale them every frame and the chart would breathe — the no-layout-shift rule violated inside the chart's own frame. They freeze at what's on screen on `pointerdown` and settle **once**, when the drag is over *and* any chunk it kicked off has landed: one controlled rescale when the viewer stops moving, never a jitter under the finger and never a jump the instant a fetch returns.
  - **Night bands are computed per day from the station's lat/lon** (issue #111, landed after #106). #106 shipped with a **7-day honesty horizon** because the browser was only ever told *today's* sunrise/sunset (repeated every 24h), and day length drifts ~2 min/day: a week out that's ~15 min ≈ 2px, invisible, but a month out it's an hour, visibly wrong — so rather than drift into fiction the bands simply stopped, and panned deep the chart had no shading. #111 removed the guesswork at the source: `weather/current` now carries the station's **lat/lon** (from OWM's `coord`), and `sunTimes` (the pure NOAA solar-position algorithm, `lib/weather.ts`, Vitest-checked against published almanac times within ±2 min) recomputes each day's sunset→next-sunrise for real. The horizon and its clamp are **gone** — `nightBands(lat, lon, ts0, ts1)` bands any window at any depth. **Honest absence stays the fallback**: a report without lat/lon (an older `weather.py` through a deploy) draws *no* bands rather than drifting ones — #106's ethos survives even though its horizon didn't.
  - **Interaction**: the first drag in the codebase, so it sets the pattern — pointer events throughout (one path for mouse and touch, as the hover scrub already did), `setPointerCapture` so a drag leaving the chart doesn't strand, and `touch-action: pan-y` so a horizontal drag pans while a vertical one still scrolls the page (the browser fires `pointercancel` when it claims the gesture, which ends the drag cleanly). Mouse hover scrubs as before and a press-drag pans, release handing hover back. On touch the two collide, so they split: **drag pans, tap places the crosshair** — a finger resting on glass isn't hovering, and today's touch-scrub is a happy accident of pointer events that a tap preserves rather than drops. A press travelling under `TAP_SLOP_PX` is a tap. The snap-back control is a `now` button in the chart's legend line, **always rendered and merely disabled while live** — a control that appeared on pan would shove the legend sideways (house rule #1) — wearing the masthead's chrome and the day-stepper's disabled idiom rather than a new vocabulary. Zoom/span presets are the acknowledged follow-up once the archive holds enough months for dragging 144h at a time to feel tedious.
- **The page is `/aviary/weather`, and `/weather` is a permanent redirect** (issue #142 first made the view a page so the launchpad's tile had a plain URL; #652 moved it under the Aviary masthead). `app/aviary/weather/page.tsx` is the mask page's shape — `force-dynamic`, `generateMetadata` over `stationBrandingFromEnv()`, so a station's tab reads "Weather Post — Karen's Aviary" — rendering `AviaryWeather`, which feeds the view from `useWeatherFeed()`, the bus subscription + staleness/presence judgements (each caller runs its own mqtt client, the self-contained idiom the panels set). All weather topics are retained, so a fresh tab paints state straight off the broker with no HTTP and no spinner-then-jump; the view's em-dash placeholders reserve the footprint for the first paint. `app/weather/page.tsx` answers `permanentRedirect("/aviary/weather")` (a 308) so bookmarks and the `weather.lan` door keep working, and the segment still owns `/weather/history` — #142's page-and-API-child arrangement, now redirect-and-API-child. `components/WeatherStation.tsx`, the thin wrapper, is gone. **Product door:** `https://weather.lan/` redirects to `/aviary/weather` (`Servers/Caddyfile-orchid`), and the station porch's weather tile points there too until the porch retires (epic #627 Phase 5). Still one Next process; the weather view is one of the Aviary's tabs now, not a peer product.
- **Precipitation wears its intensity as shade** (issue #113): each bar's ink tracks **its own value** — rate for the observed piezo bars, chance for the forecast ghosts, inches for snow — so a 90% Friday reads as a tall vivid slab and a 20% Tuesday as a short ghost without hovering. Redundant with the bar's height *on purpose*: the shade makes no claim the height doesn't already make, so it cannot be misread and needs no legend of its own. (The tempting alternative — height = chance, shade = expected *volume*, restoring what #65 banished to the hover chip — is a real candidate that needs a legend to explain it, and so wants its own issue.) Three details are load-bearing: **the ramp mixes toward `--panel` rather than varying opacity**, because the observed bars are 0.7 viewBox units wide but 5-minute points sit ~0.56 apart — they *already overlap*, and stacked translucent bars compound into intensities the station never measured (the warning that has sat in the rain strip since #56); solid fills overlap by overwriting. **The faint end is floored** so "unlikely" never reads as "no data" — and the floors differ per ink because white and blue don't vanish at the same rate: `RAIN_SHADE_FLOOR` 0.4 and `SNOW_SHADE_FLOOR` 0.3 both land at ~2.1:1 against the panel (measured, not guessed). **The forecast's ceiling stays under the observed trail's full voice** (`FORECAST_SHADE_CEIL` 0.85): a prediction, however confident, must never shout as loud as a measurement — while snow reaches *full* white, because the piezo is snow-blind so its strip has no measured sibling to out-shout. Direction is "vivid = more": on pine-black, fading a colour blends it toward the near-black panel, so faint reads **dimmer and greyer**, not lighter — which is why "solid white for heavy snow" and "stronger blue for a sure thing" are the same ramp described from opposite ends. `precipShade`/`precipFill` are pure and Vitest-covered; the normalisation is what earns the test (hand it the wrong ceiling — `rainMax` vs a fixed 100% vs `snowMax` — and every shade is wrong while still looking plausible).
- **The strips' headings read over their own data** (issue #113). They sit in the top-right corner because #56 put them in the forecast half, on the premise that the station leaves the future blank — **a premise #65 destroyed** when it rescaled the ghosts to chance on a fixed 0–100% strip, where a confident Friday is a full-height bar growing straight into that corner. So they stop relying on it: 11px in `--ink-dim` (was 10px in `--ink-faint`, the palest ink on the board) wearing a `--panel/80` **scrim**. The scrim is the part that matters — measured against the loudest possible bar the heading went from **1.80:1 to 4.98:1**, clearing WCAG AA, and bigger-and-brighter alone wouldn't have: the old label was only 3.23:1 even over bare panel. Both the heading and the left-edge scale whisper stay absolute overlays, so none of it can shift the chart.
- **Each forecast peak and valley wears its temperature** (issue #113, `tempMarks` in `lib/weather.ts`): the question a viewer actually has — how hot Friday gets, how cold tonight — answered without hovering point to point. **They are turning points, not per-calendar-day min/max, and that distinction is the whole design.** Calendar bucketing is right for *speech*, which is why `weather.py`'s `extended_digest` does exactly that for Willard's "days ahead"; it is wrong for labelling a *curve*, and it fails precisely when the chart is most worth reading — on an evening cold front the temperature falls all night, so Friday's coldest sample is 23:00 (a bucket edge, still dropping) and Saturday's is 06:00: two labels seven hours apart on one continuous slide into one valley. Turning points give that valley the single label it deserves with no special-casing of midnight. **Willard and the chart therefore answer different questions** — "how cold does Friday get" versus "where does this curve bottom out" — and will visibly disagree on exactly that night, and *both are right*; that divergence is deliberate, not a bug to file. The labelled point is always a **real** forecast point: averaging the two lows would invent a temperature nobody forecast, which is the one thing this chart doesn't do (`nearestPoint` snaps, `linePath` splits on null rather than bridging). Endpoints are never marked — the first and last points aren't turning points but where the data ran out. **The observed-side bridge is dropped outright rather than merely left unlabelled** (issue #103): `coming[0]` is `trendSeries`' seam stitch, a 5-minute trail sample wearing the forecast series' clothes, and leaving it in the array to act as a *neighbour* is enough to do the damage — it is the one sample guaranteed to sit beside the first forecast step, so on any morning climbing toward its high the last reading before the seam lands above that step and manufactures a valley the weather never had, labelled at the now line where the trail is steepest and cuts straight through the glyphs. That is precisely the 5-minute noise this function is forecast-only to avoid, readmitted one point at a time. `trendSeries` therefore reports `bridged` (only the drawn line wants that point; nothing reading the forecast can tell by looking), and `tempMarks` slices it off **before** the null filter — the bridge is `coming[0]` whatever it measured, so filtering first would eat a real step instead and the phantom would simply move one point right. The cost is a genuine dawn valley losing its label whenever it falls on the first step: that step has no forecast predecessor to turn against, which makes it an endpoint like any other, and silence beats a turning point judged against a different series. A `TEMP_MARK_MIN_GAP_S` (10h) rule thins a shower's 2°F wiggle into the real afternoon; because extrema always *alternate*, the same-kind rival is two marks back, not one — comparing only against the previous mark would never catch the pair that matters. Labels read the **blended** temps (#71 — `trend.coming` is already calibrated) or they'd disagree with the line they sit on, and they're HTML overlays for the same reason as the snapped dots (the viewBox is stretched; SVG text would squash). Forecast only: the observed trail is 5-minute data where every passing cloud is a turning point. **Caveat worth knowing**: OWM's free `/forecast` is 3-hour steps, so the labelled peak is the *sampled* peak — the true daily high may sit between two samples and run a degree or two warmer.
